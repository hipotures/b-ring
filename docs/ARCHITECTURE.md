# B-Ring — Architecture (Phase 1)

B-Ring is a self-hosted hybrid file space: Android devices (**Moons**) orbit a
Linux workstation (**Ring**). The Ring holds plain files on disk and is the
single source of truth. This document is the agreed design for Phase 1.

Ground rules that shape everything below:

- **`bring-core` has no async runtime.** No `tokio`, no `axum` — it must
  compile cleanly for Android through UniFFI.
- **One API contract.** All HTTP DTOs live in `bring-core::api` and are used by
  both the server (`bringd`) and the client (`bring-uniffi`).
- **Staging lives inside the Ring** (`<ring>/.bring/staging/`). Committed
  uploads are *hard-linked* into place, which only works within one filesystem;
  the watcher ignores `.bring/`. **Requirement:** the whole Ring (root, every
  folder and `.bring/`) must be on a single filesystem that supports hard links
  (ext4, btrfs, xfs, …; not FAT/exFAT). `bringd` checks this at startup and
  refuses to start otherwise.
- **Zero data loss.** A Moon deletes a local file only after a matching,
  verified `ACK`. Nothing on the Ring is ever overwritten by a sync.

## 2. SQLite schemas

### 2.1 Ring (`~/.local/share/bring/ring.db`)

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE meta (key TEXT PRIMARY KEY, value BLOB NOT NULL);
-- ring_id (16 B), stream_key (32 B), next_seq
-- The schema version lives in `PRAGMA user_version` (both databases), so
-- migrations need no table to exist first.

CREATE TABLE devices (
  id           INTEGER PRIMARY KEY,
  device_uuid  BLOB NOT NULL UNIQUE,          -- 16 B, generated by the Moon
  name         TEXT NOT NULL,                 -- human-readable, e.g. "Pixel 8"
  slug         TEXT NOT NULL UNIQUE,          -- path-safe, e.g. "pixel-8"; unique per Ring
  token_hash   BLOB NOT NULL UNIQUE,          -- blake3(device_token); the token is never stored
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER,
  revoked_at   INTEGER
);

CREATE TABLE files (
  id               INTEGER PRIMARY KEY,
  path             TEXT NOT NULL UNIQUE,      -- relative to ring root, NFC, '/'
  folder           TEXT NOT NULL,             -- first segment: DCIM | Download | Inbox | ...
  size             INTEGER NOT NULL,
  mtime_ns         INTEGER NOT NULL,
  mime             TEXT,
  blake3           BLOB,                      -- 32 B; NULL = hashing pending
  origin_device_id INTEGER REFERENCES devices(id),  -- NULL = desktop
  thumb_blake3     BLOB,                      -- content-addressed: thumbs/<hex>.jpg
  deleted          INTEGER NOT NULL DEFAULT 0,-- tombstone
  seq              INTEGER NOT NULL           -- monotonic change number
);
CREATE INDEX files_seq    ON files(seq);
CREATE INDEX files_blake3 ON files(blake3);

CREATE TABLE uploads (
  id              TEXT PRIMARY KEY,           -- UUIDv4
  device_id       INTEGER NOT NULL REFERENCES devices(id),
  client_key      BLOB NOT NULL,              -- blake3(path || size || blake3)
  target_path     TEXT NOT NULL,
  size            INTEGER NOT NULL,
  mtime_ns        INTEGER,
  chunk_size      INTEGER NOT NULL,
  chunk_count     INTEGER NOT NULL,
  expected_blake3 BLOB NOT NULL,
  state           TEXT NOT NULL CHECK (state IN ('open','committing','committed','failed')),
  result_file_id  INTEGER REFERENCES files(id),
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL
);
-- Only *active* uploads are unique per (device, client_key): a retry after
-- `failed` creates a fresh upload instead of hitting a constraint violation.
CREATE UNIQUE INDEX uploads_active_key
  ON uploads(device_id, client_key) WHERE state IN ('open', 'committing');

CREATE TABLE upload_chunks (
  upload_id TEXT NOT NULL REFERENCES uploads(id) ON DELETE CASCADE,
  idx       INTEGER NOT NULL,
  len       INTEGER NOT NULL,
  blake3    BLOB NOT NULL,                    -- per-chunk hash (early corruption detection)
  PRIMARY KEY (upload_id, idx)
) WITHOUT ROWID;
```

Every change to `files` (insert, update, tombstone) takes a fresh `seq` from
`meta.next_seq` inside the same transaction, so delta sync is just
`WHERE seq > ?`. `bringd` uses one serialized SQLite connection, so `seq` order
equals commit order and a client never skips a change.

## 3. HTTP API contract (`/api/v1`)

### 3.1 Transport & TLS

- **LAN:** `bringd` serves HTTPS with a self-signed certificate (`rcgen`).
  Moons pin its SHA-256 (delivered inside `sealed` during pairing), so the bearer
  token never crosses the LAN in plaintext.
- **WAN:** an optional second plain-HTTP listener bound to `127.0.0.1` (or a
  tunnel address) for a reverse proxy that terminates TLS with a real certificate.
- **Pinning verifier (`bring-uniffi`):** a custom `rustls` `ServerCertVerifier`
  that accepts the server **only if the SHA-256 of the end-entity certificate
  equals the stored pin**. It deliberately ignores SAN/IP and the CA chain, so a
  DHCP address change does not break the connection. It still delegates
  `verify_tls12_signature` / `verify_tls13_signature` to rustls' default
  algorithms, because the handshake signature is what proves the server holds
  the certificate's private key.
- **Pairing client:** `/pair/*` calls use a separate client that accepts any
  certificate. That is safe because SPAKE2 key confirmation plus the SAS
  authenticate the session, not TLS. The client records the fingerprint
  presented during pairing and aborts if it differs from `tls_cert_sha256` in
  the decrypted `sealed` result. After that, every request uses the pinning
  verifier.
- **WAN client:** standard WebPKI verification (`rustls-platform-verifier` or
  `webpki-roots`).
- **Media3 (Android):** ExoPlayer uses its own HTTP stack, so the app passes it
  an `OkHttpClient` (`OkHttpDataSource`) whose `X509TrustManager` checks the same
  `tls_cert_sha256` (and a `HostnameVerifier` that accepts the pinned cert). It
  sends `Authorization` through `DefaultRequestProperties`.
- **External players** (VLC and others, via `stream-url`) cannot pin a
  self-signed certificate. In Phase 1 they are offered only on the `wan_url`
  route, which has a real certificate. A local loopback proxy inside the app is
  a possible later addition.

### 3.2 Authentication & errors

- `Authorization: Bearer <device_token>`. The token is 32 random bytes,
  base64url-encoded. Unknown or revoked tokens get `401`.
- Lookup is by an indexed `blake3(token)` (`devices.token_hash UNIQUE`) rather
  than a constant-time comparison over all rows. A timing side channel could
  reveal at most something about the hash, never the token, and the hash is a
  one-way function of 256 random bits. `last_seen_at` is updated at most once a
  minute.
- Error body: `{"error": "<code>", "message": "..."}`. Codes: `unauthorized`,
  `not_found`, `hash_mismatch`, `missing_chunks`, `bad_chunk_length`,
  `conflict`, `expired`, `rejected`, `too_many_attempts`.

### 3.3 Endpoints

Public (no token):

| Method | Path | Purpose |
|---|---|---|
| GET  | `/health` | `{ring_id, version, protocol}`. LAN probe; `ring_id` proves this is *our* Ring |
| POST | `/pair/{pairing_id}/exchange` | `{device_uuid, device_name, spake_msg}` → `{spake_msg, ring_confirm}` |
| POST | `/pair/{pairing_id}/confirm`  | `{moon_confirm}` → `202 {status:"awaiting_user"}` |
| GET  | `/pair/{pairing_id}/result`   | `202` pending · `200 {sealed}` · `403 rejected` · `410 expired` |

`sealed = AEAD_K({device_token, device_slug, ring_id, tls_cert_sha256, lan_url, wan_url})`

Authenticated:

| Method | Path | Purpose |
|---|---|---|
| GET    | `/index?since={seq}&limit={n≤1000}` | delta sync |
| GET    | `/thumbs/{thumb_blake3}` | `image/jpeg`, `Cache-Control: immutable` |
| GET, HEAD | `/files/{id}/content` | Range / `206`, `ETag: "<blake3>"`, `Accept-Ranges: bytes`, `If-Range`, `If-None-Match` → `304`; `409` if the file changed since it was indexed |
| POST   | `/files/{id}/stream-url` | `{url, expires_at}`: signed URL (`?st=`) for players that cannot send headers |
| POST   | `/uploads` | create or resume an upload |
| GET    | `/uploads/{id}` | `{state, chunk_size, chunk_count, received:[idx…]}` |
| POST   | `/uploads/{id}/chunks/{index}` | raw body + `X-Bring-Chunk-Blake3` header |
| POST   | `/uploads/{id}/commit` | verify the file and return the ACK |
| DELETE | `/uploads/{id}` | abort; removes the staging file |

**Stream URLs.** `url` is *relative* (`/api/v1/files/{id}/content?st=…`); the
client prefixes the base URL it is using (LAN or WAN). The token is
`base64url(file_id ‖ device_id ‖ expires_at ‖ MAC)` with
`MAC = BLAKE3-keyed(meta.stream_key, …)` — a keyed BLAKE3 MAC instead of HMAC,
same guarantees, one hash function fewer. Lifetime is 6 hours (a long movie
must not expire mid-playback); revoking the device invalidates its URLs
immediately.


`origin` is the uploading device's `slug`, or `null` for files that appeared on
the desktop. A Moon knows its own slug (from pairing), not its numeric id.

### 3.5 Upload lifecycle

0. **Hash first (Moon).** Before calling `POST /uploads`, the Moon computes the
   full BLAKE3 of the file and records `hashed_size` / `hashed_mtime_ns`. That
   makes `client_key` deterministic and lets an existing file dedupe
   immediately. BLAKE3 on ARM64 runs at about 1 GB/s.
1. **Create:** `POST /uploads {path, size, mtime_ns, blake3, chunk_size?}`.
   The default chunk size is 8 MiB (allowed 64 KiB – 64 MiB). The response is
   tagged by `status`:
   - `201 {status:"open", upload_id, chunk_size, chunk_count, received: []}`
     for a new upload.
   - An *active* upload with the same `(device, client_key)` is returned as-is
     (`200 {status:"open", …, received:[idx…]}`), so resuming is idempotent.
   - `200 {status:"exists", ack:{…}}` when the path already holds a file with
     that hash, **or** when this device already committed the same
     `client_key` and the result is still on the Ring unchanged (its conflict
     name, if any). That covers a Moon that lost the commit response: it gets
     the original ACK instead of a duplicate file. `ack.upload_id` is `null`
     when the ACK did not come from a commit of this device.
   - Earlier `failed` uploads do not block a new one (partial unique index).
2. **Chunks:** `POST /uploads/{id}/chunks/{i}` → `204`.
   - The server writes each chunk with `pwrite` at offset `i * chunk_size` into
     `<ring>/.bring/staging/<id>.bring.tmp`.
   - Retrying a chunk overwrites it, so retries are idempotent.
   - Wrong length → `422 bad_chunk_length`; chunk hash mismatch → `409 hash_mismatch`.
3. **Commit:** `POST /uploads/{id}/commit`:
   1. check that every chunk is present (otherwise `409 missing_chunks`);
   2. compute the full BLAKE3 of the staging file (mismatch → `409
      hash_mismatch`, state `failed`, staging file removed);
   3. set `mtime`, `fsync(file)` → `link(staging, target)` → `fsync(dir)`.
      `link(2)` fails with `EEXIST` instead of replacing, so even a file the
      desktop creates at that instant is never overwritten (`rename(2)` would
      silently replace it);
   4. update `files` and take a new `seq` in one SQLite transaction (held
      across the link, so the watcher cannot index a half-placed file);
   5. **unlink the staging name**, leaving the Ring file with exactly one link.
      If that unlink fails (crash, I/O error), the hourly cleanup removes every
      staging file that does not belong to an `open`/`committing` upload;
   6. queue a desktop notification. Uploads within 3 s are coalesced into one
      notification ("12 files (48 MiB) received from pixel-8").
   - If the target path already holds *different* content, the existing file is
     never overwritten. The new file gets a conflict name such as
     `IMG_0042 (pixel-8).jpg`, then `IMG_0042 (pixel-8 2).jpg`, ….
   - A Ring folder on another filesystem than `.bring/staging` makes the link
     fail with `EXDEV`; the commit then fails with a message saying so.
4. **ACK:** `{upload_id, file_id, path, size, blake3, seq}`. Committing an
   already-committed upload returns the same ACK — but only while the file is
   still on the Ring with the acknowledged size, mtime and hash. Otherwise the
   server answers `409 conflict` and the Moon must upload again: a repeated ACK
   must never let a Moon delete its only remaining copy.
5. **Retention on the Moon** (`bring-core::offload`, a pure function). The local
   file may be deleted only when *all* of these hold:
   - `ack.blake3 == local_hash`,
   - `ack.size == local_size`,
   - the current file `size` and `mtime` still equal the hash-time snapshot,
   - `size > offload_threshold_bytes` (default 100 MiB).

   If all hold, the local file is deleted and the state becomes `remote-only`.
   If the file is at or under the threshold, the state becomes `synced`. Any
   error, timeout or mismatch means no delete; the entry stays in `outbox` with
   backoff.

### 3.6 Pairing protocol

- **Bootstrap payload** (binary, 31 bytes):
  `[ver 1B][pairing_id 8B][token 16B][ipv4 4B][port 2B]`.
  - It is encoded as **Crockford base32** with a check symbol and shown in
    groups of 5 characters.
  - The QR code and the manual-entry field carry the same string. A typo is
    caught locally by the checksum, so it does not burn one of the 3 attempts.
  - `wan_url` and the certificate pin arrive later, inside `sealed`.
  - The same 31 bytes travel unchanged over the sound and BLE channels
    (§3.6.1).
- **Ring identity:** the payload does not carry `ring_id`. The Moon first calls
  `GET /health` and uses the `ring_id` it reports. A wrong `ring_id` (wrong host
  or an attacker) only makes key confirmation fail; it cannot produce a session.
- **Handshake:** SPAKE2 (crate `spake2`, Ed25519 group).
  - The password is `pairing_id ‖ one_time_token`; the identities are
    `"bring-ring:" ‖ ring_id` and `"bring-moon:" ‖ device_uuid`.
  - `transcript = SHA-256` over the length-prefixed identities, device name and
    both SPAKE2 messages.
  - Keys: `HKDF-SHA256(ikm = K, salt = transcript, info = label)` with labels
    `bring/sas/v1`, `bring/confirm/ring/v1`, `bring/confirm/moon/v1`,
    `bring/seal/v1` (binding the transcript through the salt rather than the
    info string is equivalent).
  - Both sides then exchange HMAC-SHA256 key-confirmation tags over the
    transcript; `sealed` uses ChaCha20-Poly1305 with the transcript as AAD.
- **SAS:** first 4 bytes of the `bring/sas/v1` key, big-endian,
  `mod 1_000_000`, zero-padded to 6 digits.
- **Session:** TTL 5 minutes, single use, at most 3 `exchange` attempts, kept
  in `bringd` memory only.
- **Approval order:** `bring pair` waits for `y/N` on Linux. Only then does
  `/result` return `sealed` and the device is written to `devices` (with a
  unique `slug` derived from `device_name`).

### 3.6.1 Pairing channels (Phase 2)

A channel only delivers the bootstrap payload. The Moon turns whatever it
received into the text code and calls the same `pair_start`, so SPAKE2, the
SAS, the approval and `sealed` do not change. `bring pair` always shows the QR
code and the text; `--sound` and `--ble` add channels, and a channel that
cannot start prints a warning without stopping the others. Every channel stops
as soon as a Moon reaches the SAS step.

| Channel | Ring (`bring`) | Moon (Android) |
| --- | --- | --- |
| QR code | terminal QR (`qrcode`) | ZXing |
| Text | grouped Crockford base32 | text field, live checksum |
| Sound (`--sound`) | WAV played on repeat by `pw-play` / `paplay` / `aplay` / `ffplay` | "Listen": `AudioRecord` → `SoundReceiver` |
| BLE (`--ble`) | BlueZ GATT peripheral over D-Bus (`zbus`) | "Bluetooth": scan, connect, read, disconnect |

- **Sound** (`bring-core::pairing::acoustic`, ggwave-style, pure Rust, used by
  both ends):
  - 48 kHz, 4 parallel sub-bands × 16 tones, 46.875 Hz spacing, spanning
    2953 Hz. Two standard bands:
    - **Low** (default): 1875–4828 Hz, classic rendering at full level.
      Audible, works on any speaker and microphone.
    - **High** (`--sound-band high`): 18000–20953 Hz, smooth rendering at
      −25 dB. Inaudible to most adults. Field tests on an S20 FE: the mic
      port resonance peaks at 18–20 kHz, the ADC cuts at ~22 kHz, and frames
      decoded at 3 m down to −40 dB. Room reverb, not the level, causes most
      errors, so louder is not better.
    - `--sound-band <Hz>` puts the lowest tone anywhere in 1000–21000 Hz
      (rounded to a 46.875 Hz step).
    - Band sweeps and field measurements live in the separate
      [neuroson](https://github.com/hipotures/neuroson) repo (`sound-probe`).
  - Rendering: *classic* has 5 ms raised-cosine edges per symbol; *smooth*
    (`--sound-style smooth`) keeps continuous phase and glides 10 ms between
    tones at the symbol boundaries, outside the decoder window, so there are
    no clicks. `--sound-volume <dB>` (−60…0) sets the level; the defaults
    follow the band (bands ≥ 15 kHz get the high-band settings).
  - 64 ms symbols (2 bytes each) with 5 ms raised-cosine edges. The decoder's
    2048-sample Hann window skips the first 16 ms of each symbol, so most
    echo of the previous symbol falls outside it.
  - Frame: 4 preamble symbols (timing) + 25 data symbols = 1.86 s, carrying
    RS(50, 34) over `[0xB1][payload][CRC-16/CCITT]`. It repairs up to 8 bad
    bytes, and the CRC rejects the rare miscorrection. About 17 B/s of payload.
  - The decoder is streaming and amplitude-independent: each band's winner
    is judged against that band's own energy, so there is no AGC. Any
    16–192 kHz input is resampled to 48 kHz. It searches several bands at
    once (default: low and high), decodes the best-scoring passing band
    first, and reports each band's peak preamble score for diagnostics.
  - The CLI links no audio library. The WAV holds the token, so it is a
    `0600` file in the `0700` runtime directory and is removed when the
    beacon stops. `--wav FILE` saves it to play on another device.
  - Android records from `UNPROCESSED` when the device supports it, and from
    `VOICE_RECOGNITION` otherwise. It disables `AcousticEchoCanceler`,
    `NoiseSuppressor` and `AutomaticGainControl` on the session.
    It needs `RECORD_AUDIO`. "Listen" searches both standard bands, so the
    Ring alone picks one. A folded **Sound pairing** panel (pairing screen
    and app settings) tunes the bands (low + high / low / high / custom Hz),
    the detection threshold (sensitive 0.30 / default 0.45 / strict 0.60),
    the mic source (auto / raw / voice / mic / camera) and the voice
    processing. A **Sound test** panel in the app settings listens without
    pairing and without stopping at a code: live per-band scores, frames
    decoded, and a sweep over every mic source × voice processing (10 s each)
    with a table of frames, time to the first frame, level and scores.
    One-way: Linux needs no microphone, so this works on Meta Quest 3.
- **BLE** (`bring-core::pairing::ble`):
  - The Ring registers a GATT application (one primary service, one
    read-only characteristic holding the 31 raw bytes, with offset reads
    supported) and a `peripheral` advertisement (service UUID + local name
    `B-Ring`, which fits a legacy 31-byte advert) with the first powered
    adapter. It uses `zbus` (pure Rust), not libdbus. Dropping the beacon
    unregisters both, and BlueZ also drops them when the process exits.
  - No bonding: nothing appears in either OS's list of paired devices. The
    Moon asks for MTU 64, reads the value, and disconnects.
  - Android permissions: `BLUETOOTH_SCAN` (`neverForLocation`) and
    `BLUETOOTH_CONNECT`. On Android 11 (API 30) it uses the legacy
    `BLUETOOTH` / `BLUETOOTH_ADMIN` plus `ACCESS_FINE_LOCATION`, all with
    `maxSdkVersion 30`. The microphone and BLE are optional `uses-feature`s,
    and the app hides a channel's button when the hardware is missing.
- **Threat model.** Anyone in earshot or radio range can learn the payload,
  just as anyone can photograph a QR code on screen. The payload is only a
  bootstrap: an eavesdropper who races the real Moon still needs the user to
  approve a SAS that the user's own phone does not show. The session is also
  single-use and has 3 attempts.

### 3.7 CLI ↔ bringd control protocol

The CLI talks to `bringd` over a Unix socket at
`$XDG_RUNTIME_DIR/bring/bringd.sock` (directory `0700`, socket `0600`) using
JSON lines (`bring-core::ctl`). Requests: `status`, `devices`,
`revoke{device}`, `pair`. `pair` is a conversation:
`pair_payload{text, lan_url, expires_in_secs}` → `pair_sas{sas, device_name}` →
the CLI sends `pair_decision{approve}` → `pair_done{device}` |
`pair_rejected` | `pair_expired` | `pair_failed{message}`. Closing the
connection cancels the session.

### 3.8 `bringd` configuration

`~/.config/bring/bringd.toml` (optional; unknown keys are an error):
`ring_root`, `data_dir`, `lan_listen`, `proxy_listen`, `wan_url`,
`advertise_ip` (LAN IP put into pairing payloads; auto-detected otherwise),
`ctl_socket`, `pairing_ttl_secs` (300), `notifications` (true), `folders`
(`DCIM`, `Download`, `Inbox`, created at startup), `debounce_ms` (2000),
`ffmpeg` (path of the binary).

## 4. Android client specifics

- **LAN detection without location permissions.** No SSID checks and no
  `ACCESS_FINE_LOCATION` / `ACCESS_BACKGROUND_LOCATION`. The app is on LAN when:
  1. the active network has `TRANSPORT_WIFI` and `NET_CAPABILITY_NOT_METERED`, and
  2. `GET {lan_url}/health` succeeds within 1.5 s over the pinned TLS client and
     returns the expected `ring_id`.

  Otherwise traffic goes to `wan_url`.
- **Background sync** (WorkManager constraint `UNMETERED` + Foreground Service
  `dataSync`, so Samsung's job throttling on app switches and screenshots
  cannot stop an upload) runs only when the LAN check passes. The service's
  notification is the only sync notification: its status-bar icon blinks
  while a file uploads and disappears when the round ends. Finished rounds
  are listed in the in-app history only. A new file starts a round within
  seconds (MediaStore content trigger); a 15-minute periodic round and
  opening the app catch everything else. Over cellular, sync runs only when
  the user starts it manually.
- **QR scanning** uses plain **ZXing** (`zxing-android-embedded`), with no
  Google Play Services dependency. The pairing screen also has a text field for
  typing or pasting the same base32 payload, as a fallback for devices without a
  usable camera (for example Meta Quest 3). "Listen" and "Bluetooth" fill the
  same field from `bring pair --sound` / `--ble` (§3.6.1).
- **Storage access:** `MANAGE_EXTERNAL_STORAGE` (private sideloaded APK).

### 4.1 Moon sync engine (`bring-uniffi`)

- **Blocking API.** One exported `Moon` object; Kotlin calls it from
  `Dispatchers.IO` / a `Worker`. A private Tokio runtime drives `reqwest`.
  `cancel()` stops a running sync at the next file or chunk boundary;
  `TransferListener` (a foreign trait) reports upload progress.
- **Token.** `pair_finish` returns the device token; Kotlin keeps it in the
  Keystore and passes it back with `set_device_token` after every start. It is
  never written to SQLite.
- **`run_sync`** = index → local scan → outbox → index. Sync operations are
  serialized; browsing (`entries`) only takes the DB lock.
- **Local scan** walks enabled watched folders (skipping dot-files such as
  Android's `.pending-*` / `.trashed-*`, and symlinks). A watched folder that
  is missing or unreadable (unmounted SD card) is skipped *and* its files are
  not treated as deleted.
- **Outbox:** hash every pending file first (§3.5 step 0), then upload
  smallest-first, resuming via `GET /uploads/{id}`. A network error stops the
  round (the rest would fail the same way); other errors back off
  exponentially (30 s … 1 h).
- **Retention order:** the DB is updated to `remote-only` *before* the local
  file is deleted, and the file is re-`stat`ed right before the delete. A crash
  in between leaves a file the next scan re-uploads, which dedupes to the same
  ACK.
- **Path clashes.** `entries.ring_path` is unique, so:
  - `enqueue_upload` (Share Sheet) picks the first free name with the Ring's
    own rule (`bring-core::transfer::conflict_candidates`).
  - A pending upload keeps its path; an index entry for a *different* Ring file
    at that path is skipped. When the ACK names a conflict path, the entry moves
    there and the Moon rewinds its cursor to 0 (an idempotent re-read) so the
    skipped file appears.
  - The desktop replacing a `synced` file's content is handled like a Ring-side
    delete of our version (§5.1): the local copy stays, `local-only`,
    `suppressed`. The new desktop version is not listed while that row holds
    the path (Phase 1 limitation).

## 5. Sync semantics (decisions)

1. **Ring deletes a file the Moon has as `synced`.** The Moon *never* deletes
   local data because of a remote action. The entry becomes `local-only` with
   `suppressed = 1`, so it is not uploaded again.
2. **Moon deletes a file locally.** The delete is not propagated to the Ring
   (the Ring is the source of truth).
   - A `synced` entry becomes `remote-only`.
   - A `local-only` entry is dropped, along with any pending `outbox` row.
3. **Moon edits a `synced` file.** The new content is uploaded as a new file
   under a conflict name and never overwrites the Ring copy.
4. **LAN TLS:** a self-signed certificate plus a fingerprint pin (§3.1).
5. **Thumbnails:** JPEG, max 320 px, from the `image` crate. Video frames and
   files `image` fails to decode go through `ffmpeg` — decided by the decode
   result, not the extension, so a HEIC saved as `.jpg` still gets a thumbnail.
   If `ffmpeg` is missing, the file gets no thumbnail and no error.
6. **Folder layout with several Moons.** Automatically watched folders map to a
   per-device subfolder by default (`DCIM/<device_slug>`,
   `Download/<device_slug>`) through `watched_folders.ring_folder`. Only `Inbox/`
   (Share Sheet) is shared. The never-overwrite rule still applies everywhere as
   a safety net.
